# Skin structure

How the sources in `src/skin/default/` are put together. The compiler features used here
(frames, `center`, `origin="screen"`, screen families, `$screen_center`) are described in the
SkinForge wiki, page "XML+ compiler".

## Layers

```
skin.yml                      lists the screens (and families of screens)
 └ screen_X.ymlinc            one screen: a frame, plus what is inside it
    └ screenpart_Window_*     a frame: a window size class (Small, Medium, Wide, Large, Full)
       └ screenpart_WindowChrome   background, title bar, clock, logo, key bar
          └ screenpart_WindowBase  the two background panels and the key bar
```

* **Frames** (`screenpart_Window_*.ymlinc`, root `frame: "true"`) are the size classes. Their
  size comes from `frames.ymlinc` (`window_medium_width`, ...); the content area of a class
  (`window_medium_content_x`, `..._content_width`, pager and list heights) is defined there too.
* A screen places its frame with `position: "center"` and positions everything else
  **relative to the frame**. A frame offset is never written into a screen; the lint
  (`tools/lint_frame_offsets.py`) fails if one is.
* Things that really belong to the screen, not the frame, say `origin: "screen"`.
* **Parts** (`screenpart_*`) sit at their own origin: the top-left of their content is 0,0 and
  the includer's `position` carries the offset. A part that is given a `size` can use
  `$width`/`$height`; other attributes on the include become variables (`clock_font`, ...).
  A part has no "template" kind: a part used by several screens (a window skeleton such as `screenpart_ConfigScreen`,
  the key bar `screenpart_ButtonsBar`) is named for what it is, and a *Panel* is the content of one screen.
* **Screens that differ only in name (and title)** are a `screenfamily` in `skin.yml`, not
  one file each.
* Positions that follow the screen size use `$screen_width`, `$screen_height` and
  `$screen_center`, not `e`, `c` or `center`.

## Checks

* `tools/lint_frame_offsets.py` - no pasted frame offsets.
* `tools/unused_sources.py` - source files nothing reaches from `skin.yml` (`--delete` removes them).
* A refactor is verified by compiling before and after (`xmlinc.py`) and comparing the
  result; it should be identical.

## Selection, menu icons and fonts

* **The selected entry of a list is the inverse selection of Google TV:** a light grey
  (`md_inverse_surface`) with dark blue text (`md_inverse_on_surface`), in `windowstyle_0.ymlinc` and, for the lists
  of the plugins, `$backgroundColorSelected` / `$foregroundColorSelected`. Its corners are `$radius_item` (12).
  A list that sets its own selected colours (`*Selected` attributes, `color_sel`) must use the `md_inverse_*`
  roles too: a light accent such as `md_primary` is hardly visible on the grey. The grid EPG is the exception: in its
  "Graphics" mode, the default, a cell is a stretched tile (`epg/SelectedEvent.png` and the others in `epg/`), and the
  `Entry*Color*` attributes of the skin only apply to its "Text" mode; `tools/gen_icons.py` draws the tiles of the
  focused cell in the colour of the selection (the text colour still comes from the attribute).
* **Settings screens (a list of options to change) all use the Large frame.** A screen that is just the list
  with its description and footnote is a child of the `screenpart_ConfigScreen` family in `skin.yml` (a name,
  and a title where it has one). One with more content of its own (a status text, an info panel) has its own
  screen and body in `$window_large_*`, and places its extras where `screenpart_ConfigScreen` has the description
  (`20,600`). Popups, wizards and the lists of managed items (users, mounts) are not settings screens and keep
  their own size.
* **Menu icons** are Material Symbols, generated by `tools/gen_menu_icons.py` (the table of which
  symbol draws which file is in the script). Each comes twice: `<name>.svg`, outlined, and
  `<name>_selected.svg`, filled and in the dark colour of the pill. `screenpart_Menu` swaps in the
  filled one for the selected row (it is not named in `menuicons.ymlinc`; it is found next to the
  outlined one). Brand icons (`e2_emby_menu.png`, ...) have no filled variant and stay as they are.
* **The menus as a grid:** `screenpart_MenuGridBody` (screen `MenuHorizontal`, a `ScreenLarge` like the plugin
  list): 3 rows of 7 tiles (238 x 190, as in the plugin list), the description of the selected entry and the pager under them. `Screens/Menu.py` uses it
  for the main menu and every sub menu when the setting *Menu style* (System > User interface, stored in
  `config.usage.menu_style`) is *Horizontal*. With *Standard* the lists (`Menu`, `menu_<id>`, `screenpart_Menu`) are
  used as before. The plugin sets it to *Horizontal* when the skin is selected and puts it back to
  what it was when another skin is selected (`syncMenuStyle` in `plugin.py`; the value before is kept in `menu_style_before`); a choice made
  in between is left alone. If the plugin is removed while the skin is active, the setting is put back when enigma2 ends
  (`autoStart` with reason 1 writes the settings once more: the prerm cannot, enigma2 writes the file from memory when it ends). enigma2 only offers the setting when the skin has a `MenuHorizontal` screen. The tiles load their icons at
  96 px from `menuicons` in an applet (the menu hands in 48 px ones, `MenuIconSize`, which the list needs). The selected
  tile is the inverse pill of the lists with the filled dark blue icon (`<name>_selected.svg`): the applet puts a build
  function on the content of the tiles that swaps it in for the tile that is selected at the moment it is painted, as
  `screenpart_Menu` does for its list. An icon without a `_selected` variant (the brand PNGs) stays as it is.
* **The cockpit menu:** the MENU key opens `CockpitMenu` (`src/CockpitMenu.py`, a `Screens.Menu.Menu`) instead of the
  main menu: the entries of the menu tree that the user has picked (the whole tree is one key away: MENU in the cockpit menu opens it, `openMainMenu`). The skin
  draws it like any other menu (the grid with *Menu style* *Horizontal*, `menu_cockpit` / `Menu` otherwise): the tiles need the
  `menuicons` keys of their entries, `mainmenu` and `cockpit` are in the skin, a plugin can have one with its id (`moviecockpit`);
  without one it gets the puzzle piece, the menuicon `plugin`. The cockpit menu has a screen of its own, `MenuHorizontal_cockpit`
  (`screenpart_CockpitGridBody`, found first because the menu id is `cockpit`): two grids of `screenpart_CockpitGridList` on two lighter
  panels (`md_surface_container`), the sources `bouquets` and `menu` (2 rows of 7 tiles each, with a page indicator under each), 238 x 190 tiles like the plugin list.
  `CockpitMenu` fills both, gives the cursor to one list at a time (selection and focus of its renderer, CHANNEL UP / DOWN) and puts
  *Cockpit - Media* or *Cockpit - Menu/Plugins* into the title; with the list style of the menus it is one list as before.
  Where nothing is defined (the setting `cockpit` is empty, not `[]`) the cockpit is filled once with up to 7 bouquets of the TV
  (the upper list) and up to 7 plugins that the user has installed (the lower list), see `initialCockpit`; after that it is the user's.
  The cockpit items are in `config.plugins.materialskincockpit.cockpit` (a JSON list of key paths, `plugin:<id>` for the plugin
  list, `extension:<id>` for the extensions, `bouquet:<service reference>` for a bouquet of the TV, which opens the channel selection on it;
  the menu icon `bouquet` is in the skin; `service:<bouquet reference> >> <service reference>` for a channel, which zaps to it, with the menu
  icon `channel`), PREVIOUS / NEXT move the selected one, the four colour keys open the cockpit item that is
  assigned to them (`cockpit_buttons`, a JSON dict colour -> path; the footer shows its name) and TEXT (TXT, the action `showText` of the context
  `InfobarActions`, as the movie selection takes it; the footer shows it through `key_text`) opens a choice of the
  *Cockpit Editor* (the tree level by level, OK opens a menu or adds an entry, YELLOW adds a menu or an entry), the *Bouquet Editor* (the bouquets of the TV, OK or YELLOW adds or removes one) and the
  *Button Editor* (a row for each colour key, OK chooses its cockpit item; the rows have the icons `button_red` ... `button_blue`,
  dots in the colours of the keys). It is always on with this skin; there is no setup
  entry. Whoever does not want it adds `config.plugins.materialskincockpit.cockpit_menu=false` to `/etc/enigma2/settings`
  (enigma2 stopped: it writes the file when it ends): MENU opens the main menu then, as it does with another skin.
* **Fonts:** Roboto Regular for the text, Roboto Medium for the `*_emphasized` styles (Material uses 500
  there, not 700). Both are in `fonts/`.

## Known exceptions

* `screenpart_WlanStatusPanel`: the `Statustext` label is off-screen to the left, so the part
  does not start at its origin.
* `screenpart_Menu` builds its frame in a Python applet, with coordinates in the code.
* `screenpart_RcPanel`: hidden arrows at -100,-100.
